Lightweight tracking for features and technical improvements we intend to
pick up but aren't actively working on. One markdown file per item; this
README is the index.

## Adding a new item

1. Create `features/backlog/<kebab-case-slug>.md`.
2. Include YAML frontmatter with at minimum `id`, `status`, `created`,
   `owner`, and optional `depends-on`:
   ```yaml
   ---
   id: my-new-feature
   status: backlog
   created: 2026-07-25
   owner: unassigned
   depends-on:
     - some-other-slug
   ---
   ```
3. Write the body using the same section shape as existing items: **Why**,
   **Scope**, **Non-goals**, **Acceptance criteria**, **Implementation
   notes**, **Rough estimate**, **Related**. Not every section is
   required, but keep the order consistent.
4. Run `npm run backlog:sync` to refresh the index table above.

## Keeping this file in sync

Two guardrails keep the README's index and the per-item files from
drifting:

- **`npm run backlog:sync`** (see `scripts/backlog-sync.mjs`) scans every
  `features/backlog/*.md` (excluding this README) and rewrites the block
  between the `BACKLOG:START` / `BACKLOG:END` markers. Run it after
  adding, renaming, closing, or reordering items. It's a pure text
  transform — safe to re-run.
- **Pre-commit check.** The same script accepts `--check` and exits
  non-zero if the table is stale. Wire it into your commit workflow
  (husky, lint-staged, or a manual `npm run lint` step) so a stale index
  can't land on `main`.

## Status vocabulary

- `backlog` — captured, not scheduled.
- `next` — likely to be picked up in the next iteration.
- `in-progress` — active work; expect a branch or PR to exist.
- `blocked` — waiting on something external; the `depends-on` field
  should say what.
- `done` — merged. Move the file to `features/done/` (create the
  directory when the first item lands) rather than deleting it, so the
  rationale stays discoverable.
